Karu reads its configuration once, when a client is created. The client keeps that copy for as long as it lives, so changing the environment afterwards does not affect it.

karu_config_create() picks up the environment variables listed below, plus the home and cache directories Karu uses to find credential files. Empty variables are ignored. karu_config_create_empty() starts from nothing, with no environment, no default credential files, no metadata services, and no system CA bundle lookup. Use it for hermetic clients and tests. Setting a credential file, a metadata endpoint, or a ..._DISABLED=NO option on it turns that one source back on.

On top of that, options can be set for the whole client with karu_config_set_option(), or for one path prefix with karu_config_set_path_option(). For each request Karu takes the first value it finds:

Setting an option to NULL removes the value set at that level, and the next value in this order applies again.

A prefix covers the named resource and everything below it, and it only matches whole path segments, so /vsis3/team/private covers /vsis3/team/private/file but not /vsis3/team/private-copy/file. KARU_* options apply to the whole client and cannot be set per path.

Option names are case-insensitive, and Karu rejects names it does not know instead of ignoring them. Aliases are mapped to one name before any of this happens, so an alias can never override a path option written under the main name:

  • AWS_DEFAULT_PROFILE → AWS_PROFILE
  • AWS_DEFAULT_REGION → AWS_REGION
  • AWS_ENDPOINT_URL_S3 and AWS_ENDPOINT_URL → AWS_S3_ENDPOINT
  • KARU_MAX_RETRIES → KARU_MAX_ATTEMPTS
  • HUGGING_FACE_HUB_TOKEN → HF_TOKEN
  • SOURCE_PROXY_URL → SOURCE_ENDPOINT
  • CURL_CA_BUNDLE and SSL_CERT_FILE → KARU_HTTP_CA_BUNDLE

If the environment sets more than one spelling, the one listed first in the tables below wins.

These limits are per client. With several worker processes, try both KARU_IO_THREADS=1 and 4 on the real workload, including decoding, and keep the faster one. One client, tuned from measurements explains what to measure.

The four KARU_COALESCE_* values only decide how one batch is split into transfers. Nothing from a batch is kept after it ends, and a single batch can override the four values, as the API reference describes. Local files only merge ranges that overlap or touch, so the gap applies to remote reads only.

Karu looks for credentials in this order and uses the first it finds:

  1. AWS_ACCESS_KEY_ID and AWS_SECRET_ACCESS_KEY,
  2. the profile, with static keys, credential_process, or a web identity role, which AWS_ROLE_ARN and AWS_WEB_IDENTITY_TOKEN_FILE can also supply,
  3. the ECS container endpoint,
  4. IMDS, when Karu reads the environment or AWS_EC2_METADATA_DISABLED is set.

Profiles that chain roles through source_profile and IAM Identity Center (SSO) profiles are not handled natively. Use an AWS SDK and pass the result to Karu through a custom provider. A credential_process that runs longer than KARU_REQUEST_TIMEOUT is killed.

If S3 answers that a bucket lives in another region, Karu signs the request again for that region and remembers it for that bucket for the rest of the client's life.

AWS_S3_ENDPOINT is a service root. With virtual hosting, an endpoint of https://objects.example.test becomes https://bucket.objects.example.test/key; without it, https://objects.example.test/bucket/key. Virtual hosting is on by default for AWS itself and off for a custom endpoint. Buckets with a dot in the name also default to path style, because AWS's wildcard certificate does not match them. Setting AWS_VIRTUAL_HOSTING explicitly overrides both defaults.

Source Cooperative

source://account/product/key and /vsisource/account/product/key go through the Source Data Proxy. Public data needs no setup and is read unsigned. Source keeps its own credentials and callback kind, so AWS credentials are never sent to the proxy.

OptionPurpose
SOURCE_PROFILEAWS-style profile; default source-coop once signing is on
SOURCE_CONFIG_FILEAWS-style config file; default ~/.aws/config
SOURCE_SHARED_CREDENTIALS_FILEAWS-style credentials file; default ~/.aws/credentials
SOURCE_ACCESS_KEY_IDSource access key ID
SOURCE_SECRET_ACCESS_KEYSource secret; set it together with the key ID
SOURCE_SESSION_TOKENoptional session token
SOURCE_REGIONsigning region; otherwise the profile's region, then us-east-1
SOURCE_ENDPOINT / SOURCE_PROXY_URLproxy service root; default https://data.source.coop
SOURCE_NO_SIGN_REQUESTYES always reads unsigned, NO always signs

Despite its name, SOURCE_PROXY_URL is the Source endpoint, not an HTTP proxy. Use KARU_HTTP_PROXY for a proxy.

Requests are signed as soon as any Source credential option is set or a KARU_CREDENTIALS_SOURCE callback is installed. SOURCE_NO_SIGN_REQUEST=YES overrides that. SOURCE_NO_SIGN_REQUEST=NO asks for credentials even without other options and falls back to the source-coop profile.

The Source CLI writes a profile that uses credential_process:

[profile source-coop]
credential_process = source-coop creds
endpoint_url = https://data.source.coop

Run source-coop login once, then set SOURCE_PROFILE=source-coop. Karu runs the credential process and runs it again when the temporary keys are about to expire, killing it if it takes longer than KARU_REQUEST_TIMEOUT. Karu does not do the browser login or read the CLI's keyring. It also ignores the profile's endpoint_url, because the endpoint always comes from SOURCE_ENDPOINT.

Karu checks GCS_ACCESS_TOKEN, the HMAC pair, GCS_REFRESH_TOKEN, the ADC file, the service account key and last the metadata server, in that order, and uses the first it finds. Without GOOGLE_APPLICATION_CREDENTIALS or CLOUDSDK_CONFIG, the ADC file is gcloud's default one, if it exists.

The ADC file can describe a service account, a user login, or an OIDC external_account whose subject token comes from a file or a URL, with or without service account impersonation. For other external account sources, use a custom provider.

The metadata server is only tried when Karu reads the environment or when GCS_METADATA_ENDPOINT is set. GCS_METADATA_DISABLED=YES turns it off in every case.

Karu tries, in order, a connection string, a Shared Key, SAS, or bearer token; a service principal with a client secret or a workload identity token; App Service managed identity; and last the instance metadata service. That last one is only tried when Karu reads the environment or IMDS_ENDPOINT is set.

The endpoint comes from AZURE_STORAGE_ENDPOINT, then from the connection string's BlobEndpoint or DfsEndpoint. Without either, Karu builds https://<account>.blob.core.windows.net, or .dfs. for abfs:// and /vsiadls/ paths, and honors the connection string's DefaultEndpointsProtocol and EndpointSuffix. For sovereign clouds, set AZURE_AUTHORITY_HOST, AZURE_STORAGE_SCOPE, and AZURE_STORAGE_RESOURCE as well.

Without HF_TOKEN, Karu looks for a token file the way the Hugging Face tools do, checking $HF_TOKEN_PATH, then $HF_HOME/token, then ${XDG_CACHE_HOME:-~/.cache}/huggingface/token. No file means anonymous access. A client made with karu_config_create_empty() skips the default location but still reads HF_TOKEN_PATH or HF_HOME when they are set.

Karu reads the token file again for every request attempt, so logging in or rotating the token takes effect on the next read. Surrounding whitespace is trimmed, and a file that exists but cannot be read is a credential error.

Plain HTTP and Hugging Face requests follow redirects. Signed cloud requests report a redirect as an error instead, so their credentials and signatures are never sent to another address. Hugging Face drops the token when it follows the redirect to its CDN. When KARU_HTTP_HEADERS is set, Karu refuses any redirect to a different scheme, host, or port, so the configured headers never leave the original server. A Hugging Face file that redirects to the CDN then fails.

Karu writes Range and Host itself, along with any header it already adds to the request, and KARU_HTTP_HEADERS cannot replace them. Cloud and Hugging Face requests also refuse Authorization, Date, If-Match, and any x-amz-, x-goog-, or x-ms- header; use the credential options or a custom provider for those.

Transfers and their redirects only use HTTP and HTTPS.

When no CA option is set, a client made with karu_config_create() looks for the system CA bundle on Linux and macOS at run time, instead of relying on the path libcurl was built with. With OpenSSL, if libcurl's default directory holds hashed certificates, as on Debian and Ubuntu, Karu uses only that directory. Otherwise, with libcurl 7.87 or newer, it uses the bundle alone so libcurl can cache it for up to 24 hours; a changed bundle may not be noticed until then. Setting KARU_HTTP_CA_PATH adds a directory. Other TLS backends keep libcurl's defaults.

Custom providers

A callback installed with karu_config_set_credentials_provider() replaces Karu's own discovery for AWS, GCS, Azure, or Source Cooperative. Karu calls it with the canonical VSI path of the object it is about to read. The API reference gives the callback's signature, the fields each provider uses and the rules the callback must follow. This section covers how Karu reuses and refreshes what it returns.

Without a cache_prefix, Karu calls the provider for every request. That is the right choice when the provider or the cloud SDK already caches. With a prefix such as /vsis3/team-bucket/, Karu reuses the value for every object under it until it nears expiry. Only use a prefix the credentials are valid for.

Source Cooperative credentials are cached apart from AWS credentials, and their prefixes start with /vsisource/, not /vsis3/.

Refreshing is lazy, with no background thread, as How Karu reads describes. When credentials are close to expiring, the next request for that path calls the provider, and other requests for the same path wait for that one call. "Close" means the last tenth of their lifetime, but never more than 60 seconds or less than 1 second before expiry. Callback values without an expiry stay valid until an authentication error or the end of the client. Static credentials Karu loads itself are checked again every minute, so a rotated profile is picked up.

How configuration reaches a request

The configuration is settled once, when the client is built. For each request Karu looks up the options for the object's canonical path, loads credentials for that scope, and then builds the request.
