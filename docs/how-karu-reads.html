How Karu Reads

Karu answers one question: give me these bytes, from these objects, now. Everything below explains what stands between that question and the answer when the bytes are eighty milliseconds away, behind a signature, on a service that sometimes returns 503.

Karu 0.2.0 C++23 · libcurl 7.83+ · OpenSSL 3 Assumes C++, assumes nothing about object storage

The order matters. Part I is the problem, Part II the network facts the design rests on, Part III the API you call, Part IV the machinery behind it, and Parts V through VII what happens when things go wrong and how to run the result. Skipping Part II is the common mistake: most of the engine looks arbitrary until you know what a TLS handshake costs and what returning zero from a libcurl callback does.

Code references name files, not line numbers, because line numbers rot. Measurements name the machine. Comparisons with other libraries name the file or document they came from, and they describe those projects as they are, not as foils.

Part I The problem Why a whole library exists for something that is one system call on a local disk.

1What a range read costs

On a local disk, reading 4 096 bytes starting at byte 1 048 576 is one call: 

pread(fd, buffer, 4096, 1048576);

A few microseconds when the page is warm. The kernel puts exactly the bytes you asked for into exactly the buffer you named. There is no network, no authentication, no retry, no format to negotiate.

Karu's operation is conceptually the same one. It is called a positional read because the offset travels inside the request rather than living in a cursor that moves. No seek, no tell, no shared state between reads. Two threads can read the same object at the same time without coordinating, because there is nothing to coordinate.

That choice comes first and everything else follows from it. A cursor API forces either a mutex per open file or a handle per thread. A positional API forces neither, which is what makes a batch of a thousand unrelated reads a natural thing to express rather than an awkward one.

2An object store is not a filesystem

The tempting shape for a storage layer is open, seek, read, close. The differences that defeat it are not about speed; they are about meaning.

 Local fileRemote object
Openinga descriptor, microsecondsdoes not exist; either you make a request or you do nothing
One read1–100 µs20–200 ms of round trip
Partial readfree, at any offseta full HTTP request with headers and a signature
Mutabilitychanges underneath youobjects are replaced, not edited
Metadatastat, nearly freeanother request
Failurerare and fatalroutine and transient

Three consequences run through the whole design.

Latency dominates, not bandwidth. Asking S3 for 4 KiB and asking for 4 MiB cost nearly the same in round-trip time. What hurts is the count of requests. That is where coalescing comes from (§24): merge nearby ranges into one request even though you download bytes nobody asked for.

Failure is part of the normal path. A client that treats 503 as fatal is unusable at scale, so classification, backoff and jitter are core machinery rather than a wrapper (§32–§33).

There is no open to amortize. With no descriptor, every read carries the whole weight: resolve credentials, build a URL, sign it, find a connection. Most of the engineering in Karu is about amortizing things that a local file gets for free.

3Little's law, and the only lever

The most important result here fits on one line. In a stable system, in-flight = rate × latency. Rearranged: rate = concurrency / latency. With a typical 60 ms round trip for a small GET:

In flightLatencyRequests/s
160 ms17
860 ms133
6460 ms1 067
25660 ms4 267

You cannot lower S3's latency. You can raise how many requests are in flight. That is the whole reason KARU_CONCURRENCY defaults to 64 and the reason a carefully written sequential client still tops out in the low tens of requests per second.

The other half of the law matters just as much. Anything that stalls the state machine holding those requests open drops effective concurrency to zero while it stalls. A network call for credentials on the wrong thread is not a small regression; for its duration it is a total one. §42 is about which thread does what, and this is why it exists.

4The workload Karu is shaped around

Karu was not designed in the abstract. The target is a machine-learning dataloader that performs on the order of a million small range reads per epoch — image tiles, compressed frames — spread across thousands of objects.

  • Batches, not single reads. The consumer already knows the sixty-four ranges it needs. An API that accepts one read at a time throws that information away, so submit and fetch take an array.
  • Fixed cost per read is budget. At a million reads, fifty microseconds of overhead is fifty seconds an epoch. An allocation that is noise elsewhere is a line item here.
  • No data cache. A dataloader shuffles; a block cache would miss most of the time and would spend the memory the model needs. Karu caches credentials, connections and TLS sessions, which are reused, and never object bytes, which are not.
  • It must survive fork. PyTorch's DataLoader forks workers. A client with inherited threads is a trap, which is why §42 ends where it does.

5Where Karu stops

Karu does three things.

resolve
Turn a string — s3://bucket/key, /vsis3/bucket/key, /tmp/file.tif, hf://datasets/org/repo/x — into a structured object.
read
Given a batch of (object, offset, length, destination), fill the destinations.
size
Report how many bytes are visible through an object.

The list of what it will not do is just as informative.

  • It does not write. No PUT, no multipart, no delete.
  • It does not list. Discovering what lives under a prefix is another layer's job.
  • It does not cache object data or metadata. karu_client_size makes a request every time, and the header says so.
  • It does not understand formats. GeoTIFF, Parquet and Zarr mean nothing here; Karu addresses bytes and someone above interprets them.
  • It does not emulate a filesystem. No FILE*, no std::istream, no open handle.

The narrowness is what lets the engine be aggressive. With no writes, every request is idempotent and safe to retry without thought. With no data cache, there is no invalidation to reason about. With no formats, the planner can merge two ranges without wondering whether it just crossed a semantic boundary.

Part II Foundations HTTP, TLS and libcurl at the depth needed to see why the engine looks the way it does.

6HTTP, briefly

An HTTP/1.1 request is text. This is literally what crosses the socket:

GET /path/to/tile.tif HTTP/1.1
Host: bucket.s3.us-west-2.amazonaws.com
Range: bytes=1048576-1052671
Authorization: AWS4-HMAC-SHA256 Credential=...
x-amz-date: 20260910T120000Z

A request line, Name: value headers, a blank line. The response has the same shape:

HTTP/1.1 206 Partial Content
Content-Range: bytes 1048576-1052671/2147483648
Content-Length: 4096

<4096 binary bytes>

Headers are separated by CRLF. That is why Karu rejects any header name or value containing \r or \n. Let a newline through a user-controlled value and the caller gets to append headers of their own. The check is applied wherever headers are assembled — build_headers, credential_request, and add_configured_headers.

Status arrives before the body. A client can decide what to do with a body while receiving it, because the status line and headers came first. Half a dozen decisions in Part IV depend on that.

One TCP connection can serve many requests. Without HTTP/1.1 keep-alive none of this is viable (§10).

7Range, 206 and 416

The Range header is what turns HTTP into a random-access medium. Karu always sends the closed form: 

Range: bytes=<first>-<last>      // both inclusive

Never the open form bytes=100- and never the suffix form bytes=-500. A closed range can be validated exactly: you know precisely how many bytes should arrive, so a server that returns something else is caught rather than trusted.

A server that honours the range answers 206 with:

Content-Range: bytes 1048576-1052671/2147483648
               │       │       │        └─ total object size ('*' if unknown)
               │       │       └────────── last byte, inclusive
               │       └────────────────── first byte
               └────────────────────────── unit, always "bytes"

parse_content_range reads it and valid_content_range checks it against what was asked. The response is accepted only when the first byte matches the requested offset, the last byte does not exceed the requested one, and either it equals the requested last byte or it is the final byte of the object.

That last clause is the subtle one. Ask for bytes=0-4095 of a 1 000-byte object and the correct answer is bytes 0-999/1000: shorter than requested and entirely legitimate. Karu accepts it, delivers 1 000 bytes, and marks only the parts that fell past the end with KARU_ERR_RANGE.

416 Range Not Satisfiable arrives when the range starts past the end, carrying Content-Range: bytes */1000. Karu uses this for one specific case: a zero-byte object answers 416 with bytes */0 even to Range: bytes=0-0. The size probe (§31) recognises that shape and reports a size of zero rather than an error.

RFC 9110 §14 — Range Requests

8When the server ignores your Range

Range is a request, not an instruction. A server may legally ignore it and answer 200 with the whole object. Misconfigured proxies do it, some CDNs do it, and so do partial S3 implementations.

That leaves two bad options: download two gigabytes to throw them away, or fail. Karu takes a third — discard up to a limit, fail past it. In write_callback: 

if (transfer.http_status == 200 && transfer.offset > 0) {
    if (transfer.offset > transfer.range_fallback_limit) {
        transfer.range_fallback_rejected = true;
        return 0;                     // abort the transfer
    }
    transfer.skip = transfer.offset;  // silently drop the prefix
}

The limit is KARU_RANGE_FALLBACK_LIMIT, 8 MiB by default. Below it the prefix is dropped and the caller gets correct bytes. Above it the error names the number to change: 

https://host/obj: server ignored Range; refusing to discard 2147483648 bytes (limit 8388608)
Why a limit and not a flag

A client that always fails is brittle against mediocre servers. A client that always discards can pull gigabytes without saying so. A limit turns a policy question into a number an operator can move, and the error message says which number.

9The cost of a handshake

Opening a fresh TLS connection costs, at minimum:

  1. DNS resolution, cacheable;
  2. the TCP handshake, one full round trip;
  3. the TLS handshake, one round trip on TLS 1.3 and two on 1.2;
  4. certificate chain verification, which is real CPU work.

At 30 ms of network latency that is 60–90 ms before a single byte of the request goes out. Against that, the request itself is free.

The failure mode this produces is nasty because it is not an error. If every transfer opens its own connection, every read pays its own handshake, and throughput goes flat in a way that adding concurrency does not fix. Nothing in a functional test catches it. Three mechanisms in Part IV exist to keep it from happening: reusing easy handles so their connection caches survive (§12), sharing DNS and TLS sessions between handles (§12), and choosing carefully when an abort is worth the closed connection (§14, §37).

10Keeping a connection

HTTP/1.1 leaves the connection open after a response. If the next request goes to the same origin — scheme, host and port — it can travel on the same connection and skip all three handshakes.

In libcurl this happens by itself, with one condition that is easy to break: the connection cache lives inside the easy handle. Destroy the handle and you destroy the cache. Reset it and you keep it.

libcurl, curl_easy_reset

It resets all options to their defaults but does not change live connections, the SSL session cache, the DNS cache, cookies, or shares.

curl.se — curl_easy_reset

That paragraph is the entire reason Karu keeps a pool of easy handles instead of creating and destroying them. Each pooled handle carries its open connections with it.

The other way to lose keep-alive is aborting mid-response. When a write callback returns something other than what libcurl expects, the connection is marked unusable and closed, because libcurl can no longer know where in the stream it stopped. §14 and §37 are about when that trade is worth making.

11HTTP/2, and why the default is 1.1

HTTP/2 carries many concurrent requests over one TCP connection as independent streams. On paper that is ideal here: sixty-four ranges in flight behind a single handshake. Two objections get in the way.

The server has to speak it. Negotiation happens in ALPN during the TLS handshake, so it is directly observable — offer both protocols and see what comes back: 

curl -v -o /dev/null https://s3.us-east-1.amazonaws.com/ 2>&1 | grep ALPN
EndpointALPN result
s3.us-east-1.amazonaws.comhttp/1.1
*.blob.core.windows.netno agreement, falls back to HTTP/1.1
storage.googleapis.comh2
huggingface.coh2
data.source.cooph2

The two most used backends are on the wrong side of that table. Forcing HTTP/2 breaks nothing, since libcurl falls back, but against S3 and Azure Blob it gains nothing either.

One connection has one congestion window. Sixty-four multiplexed streams share the throughput of a single tunnel. For many small requests that is fine; for large parallel downloads several TCP connections usually win.

Karu sets KARU_HTTP_VERSION=1.1 by default and leaves the door open: AUTO, 2TLS, 2 and 2PRIOR_KNOWLEDGE are all accepted, and the multiplexing machinery — CURLMOPT_PIPELINING set to CURLPIPE_MULTIPLEX, plus CURLOPT_PIPEWAIT enabled only when an HTTP/2 version is selected — is already wired for when it is turned on.

Why the version is set rather than inherited

libcurl's own default for CURLOPT_HTTP_VERSION has changed three times: 1.1 through 7.62, 2TLS from 7.62 to 8.12, and NONE from 8.13. Karu supports libcurl from 7.83 upward, so it cannot assume any of them and states the version explicitly.

curl.se — CURLOPT_HTTP_VERSION

12easy, multi and share

libcurl exposes three objects, and understanding them is understanding the engine.

CURL *easy
One transfer. Holds the options and, crucially, its own connection cache. curl_easy_perform runs it synchronously.
CURLM *multi
A set of easy handles progressing together on one thread. An event loop: you push it, it advances everything it can without blocking.
CURLSH *share
State shared between handles — DNS cache, TLS sessions, cookies, connections. You must supply the locking callbacks.

Karu uses all three. The multi is the heart of the I/O thread. Easy handles are recycled through a pool. The share is configured with exactly two kinds of data: 

require_shared_data(share_.get(), CURL_LOCK_DATA_DNS);
require_shared_data(share_.get(), CURL_LOCK_DATA_SSL_SESSION);

One obvious candidate is missing: CURL_LOCK_DATA_CONNECT, which would share the connection cache. Leaving it out is deliberate.

libcurl, CURLSHOPT_SHARE on CURL_LOCK_DATA_CONNECT

Sharing connections across multiple concurrent threads is not supported.

curl.se — CURLSHOPT_SHARE

Karu's size probe (§31) runs on the calling thread rather than the I/O thread, so sharing connections between the two would be exactly the scenario the documentation rules out. DNS and TLS sessions are safe to share given the locking callbacks, and they carry most of the benefit.

13The event loop

The multi interface is driven by three calls. This is the skeleton of Engine::io_loop: 

while (!stop) {
    // 1. advance every transfer until it would block
    curl_multi_perform(multi, &running);

    // 2. collect the ones that finished
    while (CURLMsg* m = curl_multi_info_read(multi, &left)) {
        if (m->msg == CURLMSG_DONE) { /* ... */ }
    }

    // 3. sleep until a socket wakes up or the timeout expires
    curl_multi_poll(multi, nullptr, 0, timeout_ms, &n);
}

curl_multi_perform never blocks: it makes all the progress it can and returns. curl_multi_poll does sleep, and it is what keeps the loop from burning a core.

That raises the obvious question — if the thread is asleep in poll and new work arrives from another thread, how does it wake? curl_multi_wakeup is safe to call from any thread and makes an in-flight poll return immediately. Karu calls it when a batch is submitted, when one is cancelled, and when a credential resolution finishes.

libcurl, curl_multi_info_read

The data the returned pointer refers to does not survive calling curl_multi_cleanup, curl_multi_remove_handle or curl_easy_cleanup.

curl.se — curl_multi_info_read

Read that carefully: removing the handle and then reading msg->data.result reads memory the contract has already invalidated. Karu copies the easy handle and the result code into locals before touching the multi.

14Returning zero

libcurl delivers data by pushing it into your functions. Karu registers two:

CURLOPT_HEADERFUNCTION  →  header_callback(data, size, count, userdata)
CURLOPT_WRITEFUNCTION   →  write_callback (data, size, count, userdata)

Each receives a chunk and returns how many bytes it consumed. The contract is blunt, which is what makes it expressive:

size*count
Fine, keep going.
anything else
Abort. libcurl ends the transfer with CURLE_WRITE_ERROR and closes the connection, because it can no longer know where the stream stopped.

That "anything else" — in practice, zero — is a flow-control tool. Karu uses it in four places, each a decision:

  1. a 206 whose Content-Range does not match, rather than accept bytes from the wrong place;
  2. a 200 whose offset exceeds the discard limit, rather than swallow gigabytes (§8);
  3. the requested range is complete and the remaining body is large, rather than download it for nothing (§37);
  4. an error body exceeded its drain budget (§37).

There is a fifth case where Karu deliberately does not return zero: when the leftover body is small, it finishes reading it so the connection stays reusable. The arithmetic of that choice is §37.

Part III The surface What you actually call, and what the calls promise.

15A C ABI with a C++ facade

The stable interface is C. karu/karu.h exposes opaque handles, plain structs and status codes, and nothing else. The reason is reach: Karu has to be callable from Python, R and Julia, and a C ABI is the only interface all three speak natively. A C++ ABI would tie every binding to one compiler and one standard library.

karu/karu.hpp is a header-only facade over that ABI, not a second implementation. It gives C++ callers std::expected, std::span, RAII handles and move-only types: 

auto config = karu::Config::from_environment().value();
auto client = karu::Client::create(config).value();
auto object = karu::Object::parse("s3://bucket/data.bin").value();

auto bytes = client.read(object, 0, 4096).value();

Every one of those types wraps a C handle in a unique_ptr with the matching free function, and every fallible call returns karu::Result<T>, which is std::expected<T, karu::Error>. Nothing throws.

The version handshake is karu_api_version(), currently 1. Structures that a caller allocates and that may grow — today karu_submit_options — begin with a struct_size field so a newer library can serve an older caller (§25).

16Objects and paths

karu::Object::parse — karu_resolve in C — turns a string into a resolved object. It performs no I/O and touches no credentials; it is pure parsing, which is why it is cheap enough to call in a loop.

The VSI spelling is borrowed from GDAL's virtual file system prefixes, so paths already written for GDAL resolve here unchanged. The borrowing is deliberate and partial: Karu implements the prefixes above and rejects everything else with a message naming what it does support. There are no _streaming variants, because every remote read is already stateless.

GDAL — Virtual file systems

Whatever spelling goes in, a canonical VSI path comes out. That canonical form is what path-scoped options and credential scopes match against (§19), so s3://data/x and /vsis3/data/x behave identically.

17Byte windows

Two constructs narrow an object to a sub-range before any read happens.

/vsisubfile/OFFSET_LENGTH,<path>
<path>#bytes=FIRST-LAST

Both produce a window with an offset and a length. Reads are then addressed relative to the window, and a read that leaves it fails with KARU_ERR_RANGE before a request is built.

They compose. #bytes defines the inner window, and each surrounding /vsisubfile offset is relative to the window beneath it. Nesting is capped at sixteen levels, which is a guard against a pathological path rather than a meaningful limit.

The interesting consequence is invisible from outside. Two reads that arrive through different windows over the same underlying object are recognised as the same resource by the planner, because offsets are made absolute before anything is grouped (§23). A read through /vsisubfile/100_500,s3://b/k at offset 0 and a read of s3://b/k at offset 100 are the same ten bytes, and they can share one request.

18Configuration is a snapshot

karu::Config::from_environment() reads the supported environment variables once, along with the home and cache directories used for default credential discovery. Config::empty() starts with none of that, which is what hermetic tests want.

Client::create then copies the configuration into an immutable snapshot. From that moment the client never reads the environment again. Changing AWS_REGION in the process afterwards has no effect on an existing client, and that is the point: a request built at second one and a request built at second nine thousand are built from the same inputs.

Unknown option names are rejected rather than ignored. A typo in AWS_SECRET_ACCESS_KEY should be a configuration error, not an authentication failure twenty minutes later.

Client::matches(config) reports whether a configuration would produce the client you already have, without performing I/O. It exists so a long-lived process can decide whether to keep a client — and its warm connections — or build a new one.

19Path scopes

Options apply either to the whole client or to a path prefix, and the longest matching prefix wins: 

config.set("AWS_REGION", "us-west-2").value();
config.set_path("/vsis3/public/",  "AWS_NO_SIGN_REQUEST", "YES").value();
config.set_path("/vsis3/private/", "AWS_PROFILE", "research").value();

Matching stops at segment boundaries. A rule for s3://data covers s3://data/file and does not cover s3://data-private/file. The same rule governs the cache_prefix a custom credential provider may return (§41), so a credential scoped to one bucket cannot leak into a similarly named one.

Options whose names begin with KARU_ are client-wide and cannot be path-scoped. They describe the engine — concurrency, timeouts, the planner — and an engine has one of each. Per-batch planner settings are the deliberate exception, and they go through a different door (§25).

Aliases are canonicalised before precedence is evaluated, so AWS_DEFAULT_REGION in the environment cannot quietly outrank AWS_REGION set on a path.

20Reads, batches and completions

A read names an object, an offset and a destination:

struct Read {
    const Object* object;
    std::uint64_t offset;
    std::span<std::byte> destination;   // length comes from the span
    void* tag;                          // yours, returned untouched
    std::string_view if_match;          // optional ETag precondition
};

There are two ways to run a batch of them.

fetch is blocking. It submits, waits for everything, and returns either success or the first failure. It is the right call when you cannot proceed until all the bytes are present.

submit returns a Batch, and Batch::next yields one completion at a time as they finish, in whatever order they finish: 

auto batch = client.submit(reads).value();
while (true) {
    auto event = batch.next().value();
    if (event.state == karu::BatchState::end) break;
    decode(event.tag, event.bytes_read);   // work while the rest is still moving
}

The tag is how a caller reconnects a completion to its own bookkeeping. Karu never interprets it. For a decoder this is the whole point: frames become decodable as they land instead of after the slowest one.

Several threads may consume the same batch. next accepts a timeout: negative blocks, zero polls, positive waits. Freeing a batch cancels whatever is still pending and waits for workers to let go of the destination buffers, which is what makes it safe to free the buffers immediately afterwards.

21What you may read back

A completion reports bytes_read, and that number is the contract. Only that prefix of the destination may be inspected.

  • Success reports the full requested length.
  • An error normally reports zero.
  • KARU_ERR_RANGE may report a valid prefix: the object ended partway through the requested range, and the bytes that did exist are there.
  • Anything past bytes_read is unspecified. A failed attempt may have written into the destination before failing.

That last point matters for anyone pooling buffers. A destination handed to a failed read is not guaranteed untouched, so it must be treated as dirty rather than reused blind. If fetch fails, every destination in the batch is unspecified.

When a read's destination is left empty in the C API — buffer set to NULL — Karu allocates one and hands ownership over in the completion; release it with karu_free whatever the status. The C++ facade always supplies a destination, so this only arises through the C ABI.

Part IV Inside a read From a submitted batch to bytes in your buffer.

22The engine at a glance

A client owns one engine, created lazily on first use. The engine owns the threads, the curl multi, the share and the handle pool.

Three thread groups, with a strict division of labour. One I/O thread owns the curl multi and everything reachable from it — the pending list, the retry list, the active map, the handle pool. Four file workers serve local reads with pread. Four credential workers run profile helpers, metadata endpoints and user callbacks, all of which can block for seconds.

The reason credentials get their own threads is §3. A credential lookup that stalls on the I/O thread stalls every connection the engine is holding open.

23The planner

plan_transfers runs on the submitting thread, before any I/O, and turns N reads into M transfers where M ≤ N. It does four things in order.

Validate. A read that leaves its window, overflows its absolute offset, or asks for an ETag precondition on a local file is completed immediately with an error and never reaches a queue. These land in the batch as ordinary completions, so a caller draining with next sees them alongside the rest.

Make offsets absolute. Each read's offset is added to its window offset. From here on, everything is in coordinates of the underlying object, which is what lets reads arriving through different windows merge.

Sort. A stable sort by backend, canonical URI, ETag precondition, then absolute offset. Sorting by resource first is what groups reads of the same object together; sorting by offset within a resource is what makes coalescing a linear sweep. Reads carrying different if_match values are kept apart deliberately — they are different HTTP requests even when they address the same object.

Coalesce. Walk each group and merge neighbours while the four guards in §24 allow it. Each resulting Transfer carries a list of Parts: one per original read, each with its offset relative to the merged span, its length, its destination and its tag.

One Locator is shared by reference across all transfers for the same object, so a thousand reads of one file do not copy the parsed path a thousand times.

24Coalescing and its four guards

Merging two nearby ranges into one request trades bytes for round trips. Whether that is a good trade depends entirely on how far apart they are, so four numbers bound it.

coalesce_gap
The largest gap that may be bridged. Default 1 MiB. Zero disables merging.
coalesce_limit
The largest merged span. Default 64 MiB.
coalesce_parts
The most reads one transfer may serve. Default 1 024.
coalesce_amplification
The most bytes fetched per byte requested. Default 16.

The repository ships a benchmark that plans a batch and reports what it would fetch, with no network involved. It is deterministic, so these numbers are reproducible anywhere: 

make benchmark

One thousand reads of 64 KiB from one HTTP object, varying only the stride between them, under the shipped defaults:

PatternStrideTransfersRequestedFetchedAmplification
contiguous64 KiB162.5 MB62.5 MB1.00×
alternating128 KiB262.5 MB124.9 MB2.00×
sparse1 MiB1662.5 MB985.0 MB15.76×

The sparse row is the shape to understand. Reads a megabyte apart sit just inside the default gap, so a thousand of them collapse into sixteen requests that pull 985 MB to deliver 62.5 MB. The amplification guard is what stops it there rather than at one enormous request.

Whether that is the right trade depends on the link. Sixteen requests instead of a thousand saves roughly a thousand round trips; 922 MB of extra transfer costs about seven seconds on a gigabit link and well under one on twenty-five. Coalescing pays while the latency it saves outweighs the bytes it adds, and the crossover moves with bandwidth, round-trip time and how many requests are already in flight.

The same benchmark shows the lever. Lowering coalesce_amplification to 4 takes the sparse pattern from 15.76× to 1.00×, leaves the contiguous pattern untouched at 1.00×, and costs 1 000 requests instead of 16. Neither setting is universally right, which is why §25 exists.

Where the defaults come from

A 1 MiB gap is the same default Apache's object_store uses in coalesce_ranges. Karu adds the span, part-count and amplification bounds, which that implementation does not have. GDAL sits at the other end: its ReadMultiRange merges only strictly adjacent ranges, and its AdviseRead allows a tolerance of 2 * sizeof(uint32_t) — eight bytes, enough to bridge the two markers in a COG tile and nothing more.

25Overriding the plan for one batch

The four guards are client settings, but the caller usually knows more than the client does. A layout index knows the stride it just computed. An opening pass that reads one trailer per file across a thousand files knows those reads have nothing to merge. Rebuilding a client to say so would throw away every warm connection.

So the planner settings can be overridden for a single batch:

karu::SubmitOptions options;
options.coalesce_gap = 8 * 1024;    // this batch is sparse; do not bridge far
auto batch = client.submit(reads, options).value();

SubmitOptions holds four std::optional fields. An empty one inherits the client setting. In C the same thing is a struct: 

karu_submit_options options = KARU_SUBMIT_OPTIONS_INIT;
options.coalesce_gap = 8 * 1024;
karu_client_submit_with(client, requests, count, &options, &batch);

Two details make that struct safe to grow. Every field defaults to KARU_INHERIT, which is distinct from zero — and zero is meaningful, since coalesce_gap = 0 means do not merge at all. And struct_size, set by the initialiser to the size the caller compiled against, tells the library how much of the struct is really there. A newer Karu reading an older caller's struct simply stops at the fields that existed then.

The override affects planning only. Concurrency, timeouts and retry budget stay with the client, because they describe the engine rather than the batch.

26Scattering on arrival

A merged transfer fetches one contiguous span and owes bytes to several destinations at different offsets inside it, with gaps in between that nobody asked for.

The obvious approach is to stage: allocate the whole span, let curl fill it, then copy each part out. Karu does not do that for HTTP. Instead store_payload walks the parts with a cursor and copies each arriving chunk straight into whichever destinations it overlaps. Gap bytes are never stored anywhere.

Two properties make this worth the cursor bookkeeping. Peak memory becomes the sum of the useful bytes rather than the merged span, which at the amplification ceiling is a sixteen-fold difference per in-flight transfer. And the copying work is proportional to what was asked for rather than what was fetched.

Measured directly on an Apple M-series machine at -O2, delivering 1 000 reads through a 62.5 MB merged span in 16 KiB chunks: staging costs 3.6 ms and touches 187.5 MB; scattering costs 1.5 ms and touches 62.5 MB. At the sparse layout above the difference widens to 2.4 ms against 0.09 ms, because staging pays for the gaps twice — once to allocate, once to fill — and scattering does not pay for them at all.

Parts are allowed to overlap, so the cursor only skips past parts the current chunk cannot reach, and every remaining part that intersects the chunk is written. Two reads asking for the same bytes both get them.

One implementation note worth knowing if you read the code: the scatter path requires the transport to hand over arbitrary chunks, which curl does and pread does not. Local reads therefore keep a contiguous staging buffer (§27).

27Local files

Local reads take a different path through the same API. They go to the file workers, which open the file and issue positional reads directly into the destination.

They also get a different planning policy. For a local batch the effective gap is zero, so only ranges that overlap or touch are merged. The reason is that coalescing exists to amortize a round trip, and a pread does not have one. Reading through a gap on a local file buys nothing and costs the bytes.

Measured on the same machine, 1 000 reads of 64 KiB from a local file, comparing one pread per range against reading the merged span and copying out:

StrideOne pread eachMerged spanMerged is
contiguous, 64 KiB3.99 ms4.79 ms1.20× slower
256 KiB0.94 ms4.27 ms4.53× slower
1 MiB0.22 ms3.81 ms17.30× slower

Merging never wins, not even in the contiguous case where it saves syscalls, because the staging buffer and the copy out cost more than the calls saved. Hence a gap of zero, applied automatically by the planner when the backend is local.

ETag preconditions are not available on local files and are rejected during planning rather than silently ignored.

28Building a request in three phases

A resolved object holds no endpoint, no credential and no signature. That is deliberate: an object is parsed once and may be read a million times, while a signature is valid for minutes. Splitting them means the expensive, changing part is rebuilt exactly when it must be.

  1. Resolve the object — pure parsing, no I/O (§16).
  2. Resolve credentials for the object's canonical path, on a credential worker, through a cache (§40).
  3. Materialize the request once the byte range is known: endpoint, URL, headers, signature.

Phase three runs again for every attempt. A retry re-signs, which is what makes an expired signature recoverable and a region redirect possible: both change inputs that only phase three depends on.

The range is an input to signing, not an afterthought. SigV4 covers the Range header, so a request cannot be signed before the planner has decided what the merged span is.

29The backend contract

Every cloud backend implements the same small interface, declared in src/backends/contract.hpp:

backend
Which resolved backend it serves.
credentials_kind
Which callback slot and cache namespace it uses.
no_sign_option
The option that forces anonymous access.
credential_options
The option names whose origin defines a credential scope (§40).
load_credentials
Discovery for this provider.
prepare_request
Turn object, credentials, range and preconditions into a signed request.

Adding a backend means writing one translation unit against that contract and registering it. Nothing in the engine, planner or transport needs to know the backend exists — they see a URL, headers and a range.

Source Cooperative is the clearest illustration. It reuses the S3 signing path entirely but keeps its own credential kind, option namespace and cache namespace, so ambient AWS credentials are never forwarded to the Source proxy. Sharing a signature algorithm does not mean sharing an identity.

30Signing

Four schemes, chosen by backend and by which credential is available.

AWS SigV4S3, Source Cooperativecanonical request → string to sign → chained HMAC-SHA256 signing key

SigV4 is the involved one. The canonical request covers the method, the URI-encoded path, the query, a sorted set of signed headers and a payload hash — UNSIGNED-PAYLOAD, since these are GETs. The signing key is derived through four chained HMACs, scoping the secret to a date, then a region, then a service.

Two consequences follow. The region is part of the signature, so recovering from a region redirect means rebuilding and re-signing rather than following a Location (§34). And a signature is bound to one exact request, so signed requests do not follow redirects at all: replaying the signature at the target would either fail or send credentials somewhere they were not meant for.

31Size probes

Client::size answers how many bytes are visible through an object. If the object carries a bounded window (§17), the answer is arithmetic. For a local file it is a stat. For a remote object it is a request.

That request is a one-byte GET, Range: bytes=0-0, and the total comes from the Content-Range of the 206. A HEAD would be the obvious choice and is less dependable across object stores and proxies — some do not sign it the same way, some answer differently, some do not allow it at all. A ranged GET exercises the same path a real read will take, which means a size probe that succeeds is evidence that reads will too.

The 416 case is handled specially: an empty object answers 416 with Content-Range: bytes */0 even to a request for byte zero, and that is reported as a size of zero rather than an error.

Size probes run on the calling thread with their own pool of easy handles, separate from the I/O thread's. Results are not cached, which the header states plainly. A caller that needs many sizes should ask for them from several threads; the handle pool is built for that.

Probes share the transport's response handling with ordinary reads — the same response-state reset, the same Retry-After parsing, the same backoff — so a probe and a read fail the same way and retry the same way.

Part V When it fails Classification, backoff, and the three recoveries that are not retries.

32Classifying a failure

Every finished transfer is sorted into one of four outcomes: it succeeded, it can be recovered by changing an input, it can be retried unchanged, or it failed.

Success is stricter than a 2xx. For a 206 Karu also requires that the Content-Range matches what was asked and that exactly that many bytes arrived. A response that claims a range and delivers less is a failure, not a short read.

Retryable covers two families. By libcurl result code:

CURLE_OPERATION_TIMEDOUT   CURLE_COULDNT_CONNECT   CURLE_COULDNT_RESOLVE_HOST
CURLE_GOT_NOTHING          CURLE_SEND_ERROR        CURLE_RECV_ERROR
CURLE_PARTIAL_FILE         CURLE_SSL_CONNECT_ERROR CURLE_HTTP2  CURLE_HTTP2_STREAM

And by HTTP status: 408, 425, 429 and anything in the 5xx range. One special case joins them — a 400 whose body contains RequestTimeout, which is how S3 reports a client that stopped sending in time.

Classifying on the result code rather than on the text of an error message is a deliberate choice. A connection reset arrives as CURLE_RECV_ERROR or CURLE_SEND_ERROR regardless of how the platform words it, and error strings are not part of libcurl's stable interface.

Failures map to statuses a caller can branch on: 401 and 403 to KARU_ERR_AUTH, 404 to KARU_ERR_NOT_FOUND, 412 to KARU_ERR_PRECONDITION, 416 to KARU_ERR_RANGE, and anything else to KARU_ERR_HTTP.

33Backoff and jitter

The retry budget is KARU_MAX_ATTEMPTS, three by default, counting the first try. Between attempts the delay doubles from a 100 ms base, capped after six doublings, with full jitter added on top.

Jitter is not decoration. Sixty-four transfers that fail together and retry on an identical schedule arrive together, and a service that just asked for less load gets a synchronised burst instead. Randomising each delay spreads the second wave across the window.

A Retry-After header takes precedence when present, in both its seconds form and its HTTP-date form. It is clamped to sixty seconds, because a server asking a batch read to wait an hour is better reported than obeyed, and a small random offset is still added so a shared retry instant does not become a shared thundering herd.

Before sleeping, Karu checks the transfer deadline. A retry that could not finish before the deadline expires is not attempted; the transfer reports a timeout immediately, with a message that says the budget left no room for another attempt.

34Region redirects

An S3 request sent to the wrong region fails, and the response says where the bucket actually lives — in the x-amz-bucket-region header, or in a <Region> element inside the error body.

Karu reads both, and takes the header when it is present. This is not a redirect that can be followed: the region is an input to the SigV4 signing key, so the request has to be rebuilt and re-signed against the correct region (§30).

The discovered region is remembered on the batch, keyed by object. The first read to hit the wrong region pays for the discovery; every other read of that object in the same batch is built correctly the first time. The retry happens once per transfer and does not consume the ordinary retry budget, because it is a correction rather than a repetition.

35Expired credentials

Temporary credentials expire, and a request signed at the wrong moment fails with an authentication error rather than a network one.

Karu recognises two shapes. A 401 from GCS, Azure or Source Cooperative. And a 403 from S3 or Source whose body carries one of:

<Code>ExpiredToken</Code>
<Code>InvalidToken</Code>
<Code>RequestExpired</Code>

Either invalidates the cached credential for that scope and sends the transfer back to a credential worker for a fresh lookup, then to be re-signed. Like the region correction this happens once per transfer and sits outside the retry budget. A second authentication failure with freshly fetched credentials is a real one and is reported.

Most of the time this path is never taken, because refresh is proactive: credentials are renewed during the last tenth of their lifetime, bounded to a one-to-sixty-second window (§40). The reactive path exists for clock skew and for credentials revoked early.

36Deadlines

KARU_REQUEST_TIMEOUT, 120 seconds by default, bounds one logical read from end to end — every attempt, every backoff, every re-signature. It is not a per-attempt timeout, which would let three attempts and two sleeps run for far longer than the number suggests.

The deadline starts when the transfer first enters a worker, so credential resolution is inside the budget. It is checked before building a request, after building one, before sleeping between attempts, and when a transfer completes. Each check has its own message, so a timeout says which stage ran out of time.

Two narrower timeouts sit underneath.

KARU_CONNECT_TIMEOUT
30 s, for the connect phase alone.
KARU_LOW_SPEED_LIMIT
KARU_LOW_SPEED_TIME
1 024 bytes/s sustained below the limit for 60 s aborts the transfer. This catches a connection that is open and technically alive but making no progress, which a total timeout would only notice at the very end.

Setting the request timeout to zero removes the outer bound. Everything else keeps working; nothing then bounds total time.

37Draining a body

When a transfer has the bytes it needs, or has failed, there is usually more body still arriving. Two options: read it and keep the connection, or abort and pay a handshake next time.

Karu decides by size. Up to 256 KiB of unwanted body is read and dropped, which leaves the connection reusable. Beyond that the transfer aborts, because a full TLS handshake is cheaper than megabytes of pointless transfer.

The same budget bounds error bodies. The first 4 KiB is captured for diagnostics and for the XML that region and credential detection read; beyond 256 KiB, the response is cut short. A misbehaving endpoint cannot make a failing request expensive.

This is the fifth case from §14 — the one where returning zero would be available and is deliberately not used. Small waste to keep a connection is a good trade; large waste is not.

38Error text

Every failure carries a message alongside its status. The status is for branching; the message is for a human.

Messages are thread-local and valid until the next Karu call on that thread. In C, karu_last_error() returns it; the C++ facade copies it into Error::message so it can outlive the call.

URLs in messages are redacted before they are stored. Userinfo is replaced and everything from the first ? onward is dropped, because a presigned URL or a SAS token carries its credential in the query string. An error message reaching a log should not be a credential leak. 

https://account.blob.core.windows.net/c/blob?<redacted>: HTTP 403: AuthenticationFailed ...

Bodies are summarised rather than pasted: whitespace collapsed, truncated to 200 characters. Enough to see AccessDenied or NoSuchBucket, not enough to flood a log with XML.

Part VI Credentials Where they come from, how they are cached, and how to supply your own.

39Where credentials come from

Each backend has its own discovery order, and each begins the same way: an installed callback wins over everything else, and an explicit ..._NO_SIGN_REQUEST=YES wins over that.

For AWS the order is static options, then the named profile — including credential_process and web-identity profiles — then container credentials, then IMDS. GCS reads static tokens and interoperable HMAC keys, then Application Default Credentials, then the metadata server. Azure reads a connection string, SAS, account key or static token, then client secret, workload identity and managed identity. Hugging Face reads HF_TOKEN and then the token file the CLI writes.

Two backends are anonymous by default: plain HTTP, which has no credential concept, and Source Cooperative, whose public products need none. Configuring any Source credential option or installing a Source callback switches it to signed automatically.

Some mechanisms are deliberately out of scope — chained AssumeRole through a source profile, IAM Identity Center, environment-specific external-account suppliers. They belong to the vendor SDKs, which already implement and maintain them, and the callback in §41 is how you hand them over.

The full option tables live in the configuration reference.

40The cache and its single flight

A credential lookup can be a file read, a subprocess, or an HTTP round trip to a metadata service. Doing that per request would be absurd, so results are cached — and the interesting part is what they are cached against.

The key is not the path. It is which origin supplies each of that backend's credential options for that path: a path rule, an explicit value, the environment, or nothing. Two paths that draw their credentials from the same places share a cache entry; a path with its own AWS_PROFILE rule gets its own. The entry stays correct without being invalidated when an unrelated path is configured.

Refresh is proactive and lazy. A credential with an expiry is renewed during the last tenth of its lifetime, bounded to between one and sixty seconds before it expires. There is no background thread: the first request that arrives inside the refresh window does the work. Credentials without an expiry are re-checked every sixty seconds, so an aws sso login that rewrites ~/.aws/credentials underneath a running process is picked up.

Concurrent misses collapse into one lookup. The first request for a scope starts the load and registers it; every other request for that same scope waits on it and takes the same result. Sixty-four transfers starting together against a cold cache produce one call to the metadata service, not sixty-four.

A failed lookup is never cached. One anonymous or unavailable result must not poison later signed requests, so failures are returned to the waiters and forgotten. An expired credential is rejected rather than stored, and an invalidation that lands while a load is in flight marks that load so its result is delivered but not kept.

41Your own provider

karu_config_set_credentials_provider installs one callback per backend kind. It is how an application hands Karu credentials from a vendor SDK, a secrets manager, or anything else Karu should not know about. 

karu_status provide(void* user_data, karu_credentials_kind kind,
                    const char* canonical_path, karu_credentials* out) {
    out->access_key_id     = "...";
    out->secret_access_key = "...";
    out->session_token     = "...";
    out->expires_at        = 1789000000;      // Unix time, or 0 for none
    out->cache_prefix      = "/vsis3/team-bucket/";
    return KARU_OK;
}

The callback receives the canonical VSI path, so one provider can serve many buckets and decide per path. Karu copies every returned string before the callback returns, so the callback may own its buffers.

cache_prefix is the important field. It declares the scope over which the returned credential is valid, and it is checked: a prefix that does not contain the requested path is a configuration error rather than a silent widening. Leave it empty and Karu calls the provider for every request, which is the right choice when the provider or its SDK owns its own cache.

Three obligations come with it, all for the same reason — Karu cannot interrupt caller code.

  • It must be thread-safe. Callbacks for different paths may run at the same time.
  • It must not re-enter the same client.
  • It must bound its own I/O. A callback that hangs holds a credential worker until it returns.
Part VII Running it Threads, processes, and how to measure without fooling yourself.

42Threads and processes

A karu_client is safe to share across threads and is meant to be. One client, one engine, one connection pool, one credential cache: splitting it per thread multiplies handshakes and lookups for nothing.

Which thread runs what:

ThreadCountOwns
I/O1curl multi, handle pool, pending and retry lists, request materialization, response handling
File workers4local positional reads
Credential workers4profile helpers, metadata endpoints, user callbacks
Calleranyplanning at submit, size probes, draining a batch

Everything the I/O thread reaches belongs to it alone, which is why there are no locks in the hot path. Other threads hand work over through queues.

Forking is the sharp edge. A forked child inherits the parent's memory but none of its threads: the engine's threads simply do not exist there, and a mutex held by a vanished thread stays held forever. Since PyTorch's DataLoader forks workers by default, this is not a corner case for Karu's main consumer.

The client records the process that created its engine. On first use it compares that against the current process, and on a mismatch it abandons the inherited engine and mutex rather than touching them — allocating replacements first, then releasing the old pointers without running their destructors. Destroying a threaded engine in a child would mean joining threads that were never cloned. The pages leak, and the child exits shortly after; that is the correct trade.

The practical consequence is that a client created before a fork works in the child, transparently, by building a fresh engine on first use. It also means the child pays for its own connections, which is unavoidable — file descriptors for TLS connections cannot be meaningfully shared across a fork anyway.

43Measuring

Measuring a network client is unusually easy to get wrong, and most wrong measurements point the same way: they make the client look better than it is.

A local HTTP server measures the wrong thing. With a sub-millisecond round trip, latency stops being the bottleneck and per-request CPU takes over. Concurrency shows almost no benefit, coalescing looks like pure overhead, and connection reuse looks irrelevant. Every conclusion inverts against a real endpoint.

The first request is not representative. It pays DNS, a TCP handshake, a TLS handshake and a credential lookup. Discard a warm-up round or report it separately.

Report bytes fetched, not just bytes requested. Coalescing moves work between those two numbers. A benchmark that reports only throughput of useful bytes cannot tell a good merge from a wasteful one.

Separate what you can measure offline. Planning is deterministic and needs no network, which is exactly what make benchmark exercises: transfer counts, byte amplification and planning time for several range patterns and policies. Those numbers are stable and comparable across machines. Network numbers are neither.

When you do measure against real storage, the effect that dominates everything else is concurrency. Moving the same reads, on the same machine, from sequential to concurrent against a real bucket is a hundredfold difference in requests per second. No amount of local optimization approaches it, which is the practical restatement of §3.

One ceiling is worth knowing about. Request materialization — building the URL, headers and signature — happens on the I/O thread, so its cost per request bounds how fast the engine can issue requests regardless of the network. On an Apple M-series machine at -O2 against S3 with static credentials, that is a few microseconds per request, which places the CPU-only ceiling in the low hundreds of thousands of requests per second. Far above what any network will deliver, but it is the number that would matter first if one ever did.
